### 신규 회차가 앱에 들어오는 경로

```
토 20:45  추첨
   ↓  배치가 토 21:00~22:59 KST 20분 간격으로 실행 (+ 일 09:00·12:00)
GitHub Pages  data/manifest.json · draws-latest.json 갱신
   ↓  앱 실행 시 manifest 확인 → 최신이면 draws-latest.json(18KB) 통째로 교체
앱   최근 100회차 창이 통째로 밀린다 (1136~1235 → 1137~1236)
```

**2026-08-08에 이 흐름이 실제로 관측됐다** (아래 '무인 갱신 실증' 참조).
사용자가 할 일은 없다 — PC를 켜둘 필요도, 폰을 연결해둘 필요도 없다.
배치는 GitHub 서버에서 돌고, 앱은 **켤 때** 갱신을 확인한다.
푸시 알림은 없으므로 앱을 열지 않으면 갱신도 일어나지 않는다.

- 앱은 동행복권을 직접 두드리지 않는다(설계 원칙 1). Pages의 정적 JSON만 읽는다
- **어느 단계가 실패해도 화면은 뜬다.** 캐시 → 번들 순으로 내려간다 (§5-②)
- 증분 병합은 하지 않는다. 18KB라 통째 교체가 더 싸고 창 이동이 자연히 해결된다
- 배포 파일과 앱 번들은 **같은 내용**이다 (`APP_BUNDLE_ROUNDS` 하나로 묶음)
- **추첨 직후에는 당첨금·판매점이 확정되지 않는다.** `Draw.isSettled`
  (`totalSales > 0`)로 구분해 "집계 중"으로 표시한다. 1등이 실제로 0명인
  회차(289·295)도 총 판매금액은 정상값이라 이 기준이 성립한다

### ③ 탭 문구는 함부로 고치지 말 것

설계 문서 §7 F3이 **"예측", "확률이 높다" 표현을 전면 금지**했다.
Play 심사 대응이자 정직성 문제다. `recommend_tab_test.dart`가 금지 표현이
화면에 들어오는 것을 막고 있으니, 문구를 바꿀 때 그 테스트를 함께 볼 것.
빈도 가중은 재미 요소일 뿐 당첨 확률을 바꾸지 않는다.

### 로컬 저장은 SQLite 대신 shared_preferences

설계 문서 §9는 `drift`(SQLite)를 지정했으나, 앱이 실제로 저장하는 것은
**내 번호 몇 세트뿐**이다. 판매점·통계는 배치가 미리 계산해 작은 JSON으로
주므로 앱에서 쿼리할 일이 없다. drift는 코드 생성까지 끌고 들어오는 데 비해
얻는 게 없어 보류했다. ⑤ 판매점 탭에서 복잡한 조회가 필요해지면 그때 올린다.

### 앱 번들 회차를 100회로 정한 근거

로또 당첨금 지급 기한은 지급개시일로부터 **1년(약 52회차)** 이다. 그보다
오래된 회차는 내 번호를 대조할 실익이 없다. 100회차면 지급 기한을 두 배
여유로 덮는다. 전 회차(216KB) 대비 18KB로 줄었다.
통계 탭은 `stats.json`(전 회차 사전 계산)을 쓰므로 이 값과 무관하다.
바꾸려면 `batch/build.py`의 `APP_BUNDLE_ROUNDS` 하나만 고치면 된다.

### 배포용 파일 뽑기

```powershell
cd d:\Dev\MProject\Lotto-app
git pull                       # 번들 에셋을 최신 회차로 맞춘다
cd app
flutter build apk --release --split-per-abi   # 파일로 직접 배포 (arm64 22.8MB)
flutter build appbundle --release             # Play 업로드용 AAB
```

- **`--split-per-abi` 를 쓸 것.** 안 쓰면 61MB다 — 그중 59MB가 ABI 3종의
  네이티브 라이브러리인데 실기기는 하나만 쓴다. `x86_64`(22.5MB)는
  에뮬레이터 전용이라 사람에게 줄 필요가 없다. 보통은 `arm64-v8a`를 준다
- AAB는 Play가 기기별로 갈라주므로 이 옵션이 필요 없다
- `--split-per-abi` 는 versionCode에 접두어를 붙인다(arm64 → 2001).
  Play에 APK로 올릴 때만 신경 쓰면 되고, AAB를 쓰면 무관하다
- **디버그 APK를 남에게 주지 말 것.** 193MB이고 `DEBUGGABLE`이며,
  나중에 정식 서명 버전으로 업데이트가 안 된다(서명 불일치).
  받은 사람이 앱을 지우고 새로 깔아야 하고 저장한 번호도 사라진다

## 발로 밟아 알아낸 함정들

코드만 봐서는 모르는 것들이다. **다시 밟지 말 것.**

### 데이터

- **262회차가 데이터의 분수령이다.** 자동/수동(`winType`)도, **1등 판매점 정보도**
  262회차(2007-12-08)부터 존재한다. 261회 이하는 둘 다 아예 없다.
  동행복권이 그 시점부터 상세 정보를 공개하기 시작한 것으로 보인다.
  - 전 회차를 합산하면 자동 비율이 왜곡된다. `method_totals()`가 `fromRound`를
    함께 반환하므로 **앱은 "262회차 이후 기준"이라고 고지해야 한다**
  - 판매점 경계는 `lotto/store_era.py`의 `STORE_DATA_FIRST_ROUND`로 관리한다.
    이걸 모르면 검증이 250개 회차를 '판매점 0건'으로 오탐해 **배치가 영구 실패**하고,
    항상 빈 응답이 올 회차에 요청을 날려 IP 차단 예산을 낭비한다 (둘 다 실제로 겪음)
- 262회차 이후로는 `winType 합 == 1등 당첨자 수`가 정확히 성립 — 검증에 사용 중
- **1등 당첨자가 0명인 회차가 존재한다** (289·295 등). 판매점 0건이 정상이다
- ⚠️ **'집계 전'을 확정으로 오해하는 길이 두 군데 있었다.** 추첨 직후에는
  집계 전이라 갓 나온 회차도 1등 0명으로 보인다.
  - `collect_stores`: 그걸 '1등 없음'으로 보고 빈 판매점 파일을 캐시에
    남겼다 (2026-08-07 수정)
  - `collect_draws`: **이미 아는 회차는 다시 받지 않아** 토요일 밤의 0값이
    영원히 굳었다. 위를 고쳐도 이쪽 때문에 증상은 그대로였다 (2026-08-08 수정)
  둘 다 결과는 같다 — **신규 회차의 판매점이 영영 비고 랭킹도 그때부터 멈춘다.**
  총 판매금액으로 가른다(`collect.is_settled`) — 앱의 `Draw.isSettled`와 같다.
- ⚠️ **판매점 빈 응답을 캐시하면 파이프라인이 영구히 죽는다.** 1등이 있는
  회차인데 목록이 아직 공개되지 않아 빈 배열이 올 수 있다. 그걸 파일로
  못박으면 `validate`가 '1등 N명인데 판매점 0건'으로 걸어 `build`가 exit 1
  하고, 워크플로의 `if: always()` 커밋이 그 빈 파일을 저장소에 올린다.
  이후 모든 실행이 캐시를 읽어 같은 자리에서 죽는다 — **손으로 지워야 풀린다.**
  지금은 '아직 공개 전'으로 세어 다음 실행이 다시 받는다 (2026-08-08)
- **원본에 잘못된 지역 표기가 있다.** `전남광주 동구 충장로`(1234·1235회차 2건).
  광주는 1986년에 전남에서 분리됐으므로 성립하지 않는 표기다.
  `parse.fix_region`이 바로잡는다. **모르는 값은 짐작해서 고치지 않는다**
- **한 매장이 같은 회차에 1등을 여러 번 내는 일이 있다** (1234회차 노다지복권방

- **총 판매금액은 `wholEpsdSumNtslAmt`다.** `rlvtEpsdSumNtslAmt`는 1~5등 당첨금
  총합(판매액의 50%)이라 그걸 쓰면 화면에 실제의 절반이 찍힌다. 한 번 당했다

- **응답이 비어 있지 않다고 해서 요청한 회차가 존재하는 건 아니다.** 창(N-5~N+4)이

### 운영

- **요청을 촘촘히 보내면 IP가 차단된다.** 0.5초 간격 600회로 차단당했다
  (다른 사이트는 정상, 동행복권만 ConnectTimeout). `--delay 1.2` 이상 유지하고
  최초 백필은 `--max-stores 150`으로 끊어서 여러 번. 주간 증분은 요청 1~2회라 무관
- 판매점은 회차마다 즉시 저장되므로 중단돼도 이어받는다
- **CI에서도 요청량 상한을 걸어야 한다.** 워크플로에 `--max-stores`가 없어
  잔량 503회차를 한 번에 긁다 14분 만에 죽었다(run #1). 토요일 cron이
  20분 간격이라 실행이 겹치는 문제도 있었다. 지금은 `--max-stores 120`
- **수집이 실패해도 커밋해야 한다** (`if: always()`). 판매점은 받는 즉시
  파일로 떨어지는데 커밋 스텝이 건너뛰어지면 그 진전이 통째로 버려져,
  다음 실행이 같은 지점에서 또 죽는다 — 백필이 영영 안 끝난다.
  검증 실패 시엔 `write_outputs`가 호출되지 않으므로 잘못된 배포는 여전히 막힌다
- **`deploy`를 '변경이 있을 때만'으로 묶으면 최초 배포가 영영 안 된다.**
  run #2가 그렇게 건너뛰어졌다(백필을 로컬에서 커밋해둬 러너에 변경이 없었다).
  수동 실행(`workflow_dispatch`)은 변경이 없어도 배포하게 해 복구 수단을 남겼다
- **워크플로 로그는 익명으로 못 받는다** (API 403). 실패 원인을 보려면
  사람이 웹에서 열거나 `DATA_PAT`이 필요하다
